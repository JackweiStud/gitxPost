# X Post 联调经验记录

**项目**: `gitxPost`  
**日期**: 2026-03-09  
**范围**: X Post 短文发布，包含纯文本和图文发布  
**当前结论**: 基础功能已真实跑通，支持发文字、发图文

## 经验 1: 首次登录不要放在干净自动化浏览器里

### 要实现什么

让 `post` 功能具备可复用的 X 登录态，后续可以直接自动发帖。

### 当时怎么做

一开始尝试用 Patchright 自带浏览器或独立自动化环境打开 X 登录页，然后人工输入账号密码，希望登录成功后复用 cookie。

### 遇到问题

即使人工输入账号密码，X 仍然提示：

- `Could not log you in now. Please try again later.`

这说明问题不是“脚本自动输入账号密码失败”，而是 X 对当前浏览器环境本身做了风控判断。

### 怎么解决

改成两段式流程：

1. 首次登录只使用真实 Google Chrome profile
2. 登录必须人工完成
3. 登录态保存在真实 profile 中
4. 后续 `post` 只复用这个 profile，不再尝试自动登录

### 为何可以解决

因为 X 更信任真实用户长期使用的 Chrome 会话，而不是“干净、陌生、自动化痕迹明显”的浏览器环境。  
真正稳定的关键不是“自动化登录”，而是“人工登录一次，后续只自动化已登录后的动作”。

## 经验 2: `post` 不该继续依赖 chromedriver

### 要实现什么

让 `post` 功能在本机长期稳定运行，不因为 Chrome 升级或驱动下载失败而中断。

### 当时怎么做

最早沿用了老文章链路的思路，继续使用 `undetected_chromedriver` 和 Chrome 版本匹配机制。

### 遇到问题

实际联调中遇到：

- Chrome 大版本变化导致 driver 匹配问题
- 驱动运行时下载失败
- 出现 `403`、下载中断、内容不完整
- 稳定性依赖外部下载源和版本匹配

### 怎么解决

将 `post` 切换为：

- 真实 Google Chrome
- Patchright 通过 CDP 附着控制

也就是不再依赖 `chromedriver` 下载和版本精确匹配。

### 为何可以解决

因为这种方式直接控制真实 Chrome，会话来自本机浏览器本身，避开了 `chromedriver` 这条最脆弱的链路。  
这让 `post` 的稳定性不再被“Chrome 自动升级”和“driver 下载失败”反复打断。

## 经验 3: X 的 Post 输入框不是普通 textarea

### 要实现什么

自动把短文内容准确写入 X 的 Post 输入框，并让发布按钮可点击。

### 当时怎么做

最初按普通表单思路处理，找到元素后直接点击、输入，或者尝试把文本写进 DOM。

### 遇到问题

问题包括：

- 元素能找到，但输入不稳定
- 普通点击和输入经常失败
- 文本即使进入 DOM，发布按钮也可能还是禁用

根因是：X 的输入区是 DraftEditor 的 `contenteditable`，不是普通 `textarea`。

### 怎么解决

改成“多选择器定位 + 可编辑性校验 + 接近真实输入”的方式：

- 优先尝试 `tweetTextarea_0`
- 若结构变化，则回退到 `contenteditable="true"`、`role="textbox"`、`aria-label` 等候选节点
- 不是“找到元素就用”，而是筛选出真正可见、可编辑、未禁用的输入区
- 聚焦输入区
- 用更接近原生输入的键盘输入方式写入文本
- 输入后再验证编辑器中确实有内容
- 再检查 `tweetButton` 是否可点击

### 为何可以解决

因为 DraftEditor 依赖的是前端内部状态，不是简单的 DOM 文本变化。  
同时，X 的页面结构也可能变化，所以稳定点不在“死绑单一 selector”，而在“多候选定位 + 可编辑性筛选 + 输入结果校验”。  
只有这样，才能在页面细节变化时仍尽量找到正确输入区，并让发布按钮被真正激活。

## 经验 4: 文字进 DOM 不等于真的可发布

### 要实现什么

确保文本写入后，真正满足 X 的发布条件，而不是表面上看起来写进去了。

### 当时怎么做

中间一度以为“只要页面里出现了文本，就说明输入成功了”。

### 遇到问题

联调里出现过这种情况：

- 页面节点里能看到文本
- 但 `button[data-testid="tweetButton"]` 仍然是禁用状态

这说明 DOM 里有字，不代表 X 内部的编辑状态已经正确建立。

### 怎么解决

把成功标准改掉，不再只看 DOM，而是同时验证：

- 编辑器里确实有文本
- 发布按钮从 disabled 变为 enabled
- 点击后编辑器状态发生变化

### 为何可以解决

因为这套标准是站在“最终行为”而不是“表面现象”上判断成功。  
它能过滤掉“看起来有内容，实际上不能发”的假成功。

## 经验 5: 图片上传最稳的是直接命中隐藏 file input

### 要实现什么

实现图文 Post 的稳定上传，不受系统文件选择器和焦点干扰。

### 当时怎么做

最开始带图链路还没确认时，主要在验证浏览器能否进入 X 和保持登录。

### 遇到问题

如果走“模拟点击上传按钮 -> 弹系统文件选择器”的思路，容易受这些因素影响：

- macOS 文件选择器焦点
- 前台窗口切换
- 自动化和系统弹窗不同步

### 怎么解决

直接命中：

- `input[data-testid="fileInput"]`

然后直接设置待上传图片文件。

### 为何可以解决

因为这样绕开了系统级文件选择器交互，减少了 UI 层面的不确定性。  
对浏览器自动化来说，这通常是最稳的上传路径。

## 经验 6: 前台看到的页面，不一定就是脚本正在控制的页面

### 要实现什么

让联调过程可观察，避免“脚本明明执行了，但人眼没看到”的误判。

### 当时怎么做

一开始主要关注是否发布成功，没有专门处理“人能否看清楚过程”这个问题。

### 遇到问题

你实际看到的是：

- 过程一闪而过
- 没明显看到文字输入和图片插入
- 发布后像是 Chrome 直接结束了

但实际上帖子已经成功发出。

### 怎么解决

补了两类能力：

- 每个关键步骤都尽量把 Chrome 拉到前台
- 增加 `--observe-ms` 参数，在文本输入后、图片插入后、发布前后主动停顿

### 为何可以解决

因为 CDP 附着的目标页和用户当前盯着的前台页不一定总是完全同步。  
增加前台激活和观察停顿后，用户感知就能和脚本实际执行过程对齐。

## 经验 7: `/compose/post` 跑通了，但 `/home` 入口也要留意

### 要实现什么

让 `post` 链路在 X 页面入口变化时仍然尽量稳定。

### 当时怎么做

当前主路径是直接打开：

- `https://x.com/compose/post`

### 遇到问题

实际使用中你观察到，X 的发帖入口经常是在：

- `https://x.com/home`

这意味着未来如果 `compose/post` 的行为变化，当前实现可能会受影响。

### 怎么解决

当前先保留 `compose/post` 作为主路径，因为它已经真实跑通。  
同时把 `/home` 识别为明确的后续 fallback 方向。

### 为何可以解决

因为这不是当前阻塞问题，而是稳定性增强项。  
先保留已跑通主路径，再补 `/home` fallback，是更稳妥的迭代顺序。

## 经验 8: 自动化成功不能只看脚本返回值

### 要实现什么

建立真正可信的联调标准，避免脚本说成功，但业务其实没完成。

### 当时怎么做

早期更容易关注：

- 程序有没有报错
- 是否返回 `ok: true`

### 遇到问题

浏览器自动化里，存在很多“脚本没报错，但业务并未完成”的情况，比如：

- 文本没真正进入编辑器
- 图片没真正被 X 接收
- 按钮找到了，但仍不可点击
- 点击后没有真正提交

### 怎么解决

把联调的成功标准统一成下面这些真实业务结果：

- 文本确实进入编辑器
- 图片确实出现预览或附件计数
- 发布按钮可用
- 点击后 compose 状态消失或页面提交完成
- 时间线里真的出现目标帖子

### 为何可以解决

因为最终业务结果才是自动化项目的唯一真标准。  
只要验收口径切换到这个层面，很多“伪成功”就会被识别出来。

## 当前确认已跑通的范围

截至 2026-03-09，当前环境下已真实验证：

- 纯文本 Post 发布成功
- 单图 Post 发布成功
- 草稿模式成功
- 真实 Chrome 登录态复用成功

## 当前仍需保留的边界

- 首次登录必须人工完成
- 当前重点验证的是单图，多图仍建议专项回归
- `compose/post` 已跑通，`/home` fallback 仍建议后补
- 可观察模式适合联调，正常运行可关闭

## 一句话结论

**X Post 自动化里，最重要的不是“怎么自动登录”，而是“用真实 Chrome 人工登录一次，后续只自动化已登录后的发布动作”。**
